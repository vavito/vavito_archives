Plano completo · backend + frontend + operação

Vavito Archives.

Plano didático e executável para construir um blog pessoal completo com NestJS, Prisma, PostgreSQL, Next.js, Supabase, Resend, Render e Vercel. A organização segue sprints e tasks pequenas, inspiradas no quadro Scrum/Kanban da API Ecommerce FastAPI, e preserva o protótipo visual V2 “Minimal Mono”.

ArquiteturaMonólito modular com camadas simples
BackendNestJS + Prisma + Supabase PostgreSQL
FrontendNext.js App Router + Tailwind + Tiptap
QualidadeUnitários, integração, E2E e CI obrigatórios
01 · Direção técnica

Decisões de arquitetura

A aplicação não usará arquitetura hexagonal nesta versão. A organização será familiar para quem conhece Controller, Service, Repository, DTO e Mapper, mantendo entidades de domínio com comportamento real, uma Linguagem Ubíqua compartilhada e sem dependência de NestJS, Prisma ou HTTP.

Monólito modular

Uma única API implantada na Render, dividida por capacidades do negócio. Não haverá microserviços na V1.

DDD Light

Entidades com regras e transições de estado, sem adicionar ports, adapters, CQRS ou event sourcing.

Camadas reconhecíveis

Controller recebe HTTP; Service coordena; Repository persiste; Mapper converte; Domain protege regras.

Regra central: uma entidade pode possuir métodos como publish(), archive() e approve(), mas nunca pode consultar um repository, acessar Prisma, enviar email ou ler uma requisição HTTP.

Linguagem Ubíqua

Produto, documentação, código, API, testes e conversas técnicas devem usar o mesmo vocabulário para os conceitos do blog. Cada conceito terá um nome canônico no glossário do projeto; sinônimos só poderão aparecer como texto de interface. Como o código será escrito em inglês, o glossário fará a ligação explícita entre o termo de negócio em português e o nome utilizado na implementação.

Conceito do negócioNome canônico no códigoSignificado no Vavito Archives
ArtigoPostConteúdo autoral que nasce como rascunho e pode ser publicado, despublicado ou arquivado.
RascunhoDraftPost ainda não disponível na área pública.
PublicaçãoPublishAção de tornar um post público; não é apenas uma atualização genérica de status.
ComentárioCommentMensagem de um leitor em um post, sujeita a edição e moderação.
ModeraçãoModerationDecisão administrativa de aprovar ou ocultar um comentário.
Artigo salvoBookmarkPost guardado na biblioteca privada de um leitor autenticado.
AssinanteSubscriberPessoa que forneceu consentimento para receber a newsletter.
CampanhaEmailCampaignEnvio editorial de email preparado para um conjunto de assinantes elegíveis.
Aplicação no código: preferir post.publish(), comment.approve(), subscriber.confirm() e POST /posts/:id/publish a nomes genéricos como updateStatus(), processItem() ou changeState(). Os testes também devem descrever o comportamento usando esses mesmos termos.

Decisões de escopo da V1

  • Supabase Auth cuidará de cadastro, login, confirmação de email e recuperação de senha.
  • O NestJS validará o JWT do Supabase e aplicará autorização por função.
  • O Prisma controlará apenas as tabelas da aplicação no schema public.
  • O conteúdo do Tiptap será persistido como JSON em coluna PostgreSQL JSONB.
  • Imagens públicas ficarão no Supabase Storage.
  • Resend será utilizado no SMTP do Supabase Auth e pela API para emails da aplicação.
  • Busca inicial usará PostgreSQL, sem Elasticsearch ou serviço de busca externo.
  • Testes são parte de cada sprint e da Definition of Done.

Regra de dependência entre camadas

Controller

Pode conhecer DTOs e services. Não conhece Prisma nem implementa regra de negócio.

Service

Coordena entidades, repositories e integrações. Não conhece Request/Response.

Domain

Conhece apenas seus próprios dados, regras, enums e erros.

Repository

Centraliza queries Prisma. Não decide regra de publicação ou autorização.

Constraints essenciais

  • Post.slug, Tag.slug e NewsletterSubscriber.email devem ser únicos.
  • Reaction(profileId, postId) deve ser único: um usuário mantém somente uma reação por artigo.
  • Bookmark(profileId, postId) deve ser único.
  • Comment.parentId deve apontar para comentário do mesmo artigo.
  • Conteúdo do post deve possuir versão do schema do editor para futuras migrações.
  • Exclusões de comentários e posts publicados devem preferir soft delete/arquivamento.
07 · Domínio

Entidades com comportamento

A entidade representa o negócio, não a tabela. O Prisma modela persistência; a entidade modela comportamento e impede estados inválidos. 

stateDiagram-v2
    [*] --> DRAFT: Post.create()
    DRAFT --> PUBLISHED: publish()
    PUBLISHED --> DRAFT: unpublish()
    DRAFT --> ARCHIVED: archive()
    PUBLISHED --> ARCHIVED: archive()
    ARCHIVED --> DRAFT: restoreAsDraft()

    note right of DRAFT
      Pode editar título, conteúdo,
      tags, capa e slug
    end note
    note right of PUBLISHED
      publishedAt obrigatório
      conteúdo e slug válidos
    end note
              
export class Post {
  private status: PostStatus;
  private publishedAt: Date | null;

  publish(now: Date): void {
    if (this.status !== PostStatus.DRAFT) {
      throw new InvalidPostStatusTransitionError();
    }

    if (!this.title.trim() || this.content.isEmpty()) {
      throw new PostNotReadyForPublicationError();
    }

    this.status = PostStatus.PUBLISHED;
    this.publishedAt = now;
  }

  archive(): void {
    if (this.status === PostStatus.ARCHIVED) {
      throw new PostAlreadyArchivedError();
    }

    this.status = PostStatus.ARCHIVED;
  }
}

Post

publish, unpublish, archive, restoreAsDraft, changeSlug e updateContent.

Comment

edit, approve, hide, softDelete e validação de autor/moderação no service.

Subscriber

confirm, unsubscribe, markBounced e bloqueio de transições duplicadas.

O service carrega a entidade pelo repository, chama o comportamento e persiste o novo estado. A entidade nunca chama repository.save(this).

Decorators próprios

DecoratorOnde usarO que fazQuem interpreta
@Public()Rotas públicas de artigos, tags, contato e newsletter.Adiciona metadado para dispensar autenticação.SupabaseAuthGuard.
@Roles(Role.ADMIN)Controllers administrativos.Declara quais roles podem executar o método.RolesGuard.
@CurrentUser()Parâmetros dos controllers autenticados.Extrai o usuário validado de request.user.Parameter decorator do NestJS.
 
@Roles(UserRole.ADMIN)
@Post(":id/publish")
publish(
  @Param("id", ParseUUIDPipe) id: string,
  @CurrentUser() user: AuthenticatedUser,
) {
  return this.postsService.publish(id, user.id);
}

Responsabilidades dos guards

  • SupabaseAuthGuard: lê Bearer token, valida JWT, issuer, audience, expiração e preenche request.user.
  • RolesGuard: lê @Roles(), busca role confiável no Profile e autoriza ou retorna 403.
  • Rotas sem @Public() ficam protegidas por padrão quando o auth guard é global.
  • A chave service_role fica apenas na API; o navegador recebe somente a chave pública permitida.

11 · Qualidade

Unitários

Entidades, services, guards, mappers e validações em isolamento. Repositories e integrações são mockados.

Integração

Prisma repositories, migrations, constraints, transações e endpoints com PostgreSQL real de teste.

E2E

Fluxos completos da API com Supertest e do frontend com Playwright em ambiente controlado.

    HEALTH --> OPERATE

Checks obrigatórios

  • pnpm install --frozen-lockfile.
  • ESLint, Prettier check e TypeScript sem emissão.
  • prisma format, prisma validate e geração do client.
  • Migrations aplicadas em banco PostgreSQL vazio.
  • Testes unitários com cobertura mínima definida.
  • Testes de integração e E2E da API.
  • Build de produção do NestJS e Next.js.
  • Build do Dockerfile.
  • Playwright contra preview quando o fluxo estiver estabilizado.
A Render deve utilizar “After CI Checks Pass”. A Vercel pode criar previews por pull request, mas produção deve estar associada apenas à branch principal protegida.

Runbooks mínimos

  • API fora do ar ou health check falhando.
  • Migration falhou durante deploy.
  • Supabase Auth não envia emails.
  • Resend apresenta bounce ou bloqueio do domínio.
  • Storage cresce por imagens órfãs.
  • Banco atingiu limite de conexões.
  • Rollback do backend e do frontend.
  • Exclusão de conta e atendimento de solicitação LGPD.

Definition of Ready

  • Objetivo e usuário beneficiado estão claros.
  • Entrada, saída e regras foram descritas.
  • Os conceitos utilizados existem no glossário da Linguagem Ubíqua ou foram definidos antes da implementação.
  • Dependências e bloqueios são conhecidos.
  • Critério de aceitação pode ser testado.
  • A task cabe na sprint; caso contrário, deve ser quebrada.

Definition of Done

  • Código revisado e sem violações de lint/typecheck.
  • Regras estão na entidade/service correto, sem lógica pesada no controller.
  • Nomes de entidades, métodos, DTOs, endpoints e testes respeitam a Linguagem Ubíqua e o glossário foi atualizado quando necessário.
  • Testes unitários e de integração pertinentes foram adicionados.
  • Swagger/OpenAPI ou documentação visual foi atualizada.
  • Migration e rollback foram revisados quando houver banco.
  • CI completa passou e não existem erros conhecidos escondidos.
